## 1 引言

### 1.1 编写目的

本文档定义"黑神话山西取景地文旅指挥平台"企业级一期的全部功能与非功能需求，作为产品设计、开发、测试、部署与验收的共同依据。阅读对象包括：项目负责人、前后端开发、UI 设计、测试、部署运维及客户方（文旅局/景区）对接人。

### 1.2 项目背景

现有项目 WuKong Travel 是以游戏《黑神话：悟空》山西 16 处取景地为主题的 WebGIS 全栈演示项目（Vue 3 + Cesium/OpenLayers + Flask + PostGIS），已具备取景地浏览、空间分析、行程规划、收藏评价、管理后台等功能。

现需将其升级为**面向山西文旅局/景区管委会的、可商业化交付的企业级项目**：以**指挥调度大屏**为核心场景，配套 PC 运营工作台与公众 Web 门户，一期以模拟数据驱动，架构上预留真实数据源对接能力。

### 1.3 文档范围

涵盖三端（指挥大屏、运营工作台、游客门户）的功能需求、外部接口、数据需求、非功能需求、部署架构、交付物、风险与里程碑。不含移动端/小程序（列入二期展望）。

### 1.4 术语与缩略语

| 术语 | 说明 |
|---|---|
| B2G | Business to Government，面向政府客户的项目制交付模式 |
| 三端 | 指挥调度大屏、PC 运营工作台、游客 Web 门户 |
| 等保 2.0 | 网络安全等级保护 2.0 制度 |

## 2 项目总体描述

### 2.1 产品定位与商业模式

- **模式**：B2G 项目制产品，客户为山西文旅局 / 景区管委会，按合同交付并提供质保。
- **核心价值**：以黑神话 IP 为引流主题，为客户提供"游客门户引流 + 指挥态势可视 + 运营内容管理"一体化平台。
- **一期策略**：业务数据以模拟数据驱动大屏演示与上线试运行；所有实时/外部数据通过**数据源适配层**获取，保证二期对接票务闸机、运营商信令、视频监控等真实系统时无需改造上层代码。
- **品牌版权**：黑神话名称及官方美术素材走**官方授权**路线（授权方：游戏科学或其授权主体）。

### 2.2 目标用户与角色

| 角色 | 使用终端 | 典型诉求 |
|---|---|---|
| 文旅局/景区领导 | 指挥大屏 | 全局客流态势、应急事件一屏感知、汇报展示 |
| 指挥/值班人员 | 指挥大屏、工作台 | 实时监看、事件接报与处置闭环 |
| 景区运营人员 | PC 运营工作台 | 取景地内容维护、资讯发布、评价管理、事件处理 |
| 系统管理员 | PC 运营工作台 | 账号与角色、系统配置、审计查看 |
| 游客（公众） | 游客 Web 门户 | 浏览取景地、看天气、规划行程、收藏评价、阅读资讯 |

### 2.3 三端总体结构

```
┌─────────────────────────────────────────────────────────────┐
│                     游客 Web 门户 (Portal)                    │
│   国风暗金 UI · 取景地/地图/行程/收藏评价/资讯/天气/导航        │
└──────────────────────────┬──────────────────────────────────┘
                           │ HTTPS / REST + 短轮询
┌──────────────────────────┴──────────────────────────────────┐
│                    Flask 后端（统一 API）                      │
│  认证鉴权 │ 业务 API │ 空间分析 │ 数据源适配层 │ 外部服务网关    │
│              PostgreSQL + PostGIS（单库）                      │
└──────────────────────────┬──────────────────────────────────┘
           ┌───────────────┴────────────────┐
┌──────────▼──────────────┐   ┌─────────────▼──────────────────┐
│  指挥调度大屏 (Screen)    │   │  PC 运营工作台 (Admin)           │
│  深蓝科技风 · 2D 地图为主  │   │  内容/用户/事件/配置/审计        │
│  客流/事件/态势/巡航       │   │                                 │
└─────────────────────────┘   └────────────────────────────────┘
```

三端为同一 Vue 工程下的三个入口（路由分区：门户 `/`、工作台 `/admin`、大屏 `/screen`），共享 API 层与组件库，独立布局与视觉主题。

### 2.4 运行环境

- **服务端**：单台云服务器（公有云，互联网区），4 vCPU / 8GB 起步；Docker + Docker Compose。
- **数据库**：容器化 PostgreSQL 16 + PostGIS 3.4（与现有 docker-compose.yml 中 `postgis/postgis:16-3.4` 镜像一致），数据卷持久化，每日自动备份。
- **客户端**：Chrome / Edge 最新版本；大屏在指挥中心全屏常驻运行；门户面向公众桌面与移动浏览器自适应。
- **网络**：平台可访问互联网（调用天地图、天气、导航、短信、微信接口）。

### 2.5 设计约束

1. 技术栈限定：JavaScript/TypeScript + Vue 3、OpenLayers、Cesium、Flask，不引入团队不掌握的主框架。
2. 后端**唯一基线为 Flask + SQLAlchemy + GeoAlchemy2**；现有 `server/src` 下的 TypeScript/Express/Prisma 实现必须删除。
3. 业务数据范围锁定 16 个取景地，不做多景区层级抽象与多租户，仅保留分类字段。
4. 地图以 2D OpenLayers 为主，Cesium 3D 仅保留现有切换入口，不新增投入；Cesium 采取**冻结策略**：版本锁定、独立异步 chunk 按需加载、纳入构建验证，不允许其静态资源进入大屏/后台首屏包。
5. 规模按演示级设计（门户并发 <200、后台用户 <50），不引入 Redis、消息队列等重型中间件。
6. 前端组件库统一为 **Element Plus**（Element UI 的 Vue 3 版本）：工作台为主要使用方并做主题定制；大屏以自研科技风组件为主、不套用 Element 默认样式；门户国风页面仅在表单/弹层等交互处按需引入，三端各自维护样式 token，禁止混用风格。
7. 空间能力与路径结果口径唯一（详见 5.3），同一界面不得出现两种互相矛盾的路径/距离结果。
8. 前端构建必须配置路由懒加载与 manualChunks 分割，Cesium、ECharts、Element Plus 均为独立 chunk。

### 2.6 假设与依赖

- 客户配合提供：16 个取景地最大承载量等指标口径、主体资质（用于备案与各开放平台申请）。
- 黑神话 IP 授权在交付前完成书面确认。
- 天气、导航、短信、微信、天地图等第三方服务账号与密钥按期到位。
- 模拟数据发生器产出的客流数值仅用于演示，不作为真实统计口径对外发布。

### 3.2 指挥调度大屏

#### SR-01 大屏总览布局与自适应
- 采用 1920×1080 设计稿，整体**等比缩放**适配任意分辨率（含超宽拼接屏与 4K），不变形、不留白边。
- 经典驾驶舱布局：顶部标题栏（平台名称、实时时钟、天气）、中央 2D 地图、左侧客流板块、右侧事件/热度板块、底部滚动资讯栏；各板块支持在工作台配置开关（AD-07）。
- 视觉：暗色深蓝科技风，发光描边、数据动效；页面常驻、异常断开自动重连。

#### SR-02 客流监测与饱和度预警
| 项 | 内容 |
|---|---|
| 展示指标 | 当前在园/今日累计/本月累计游客数、16 地实时客流排行、同比环比（Mock 口径） |
| 预警规则 | 按各取景地"最大承载量"计算饱和度：<75% 正常（蓝）、75%~90% 黄色预警、90%~100% 橙色预警、≥100% 红色预警 |
| 交互 | 点击任一度景地，地图飞行定位并弹出该地点客流明细 |
| 刷新 | 30~60 秒轮询（间隔可配置） |
| 数据来源 | 一期：Mock 数据发生器；经数据源适配层读取 |

#### SR-03 客流热力图与来源地分布
- OpenLayers 热力图层按 16 地实时客流权重渲染，色阶随预警级别变化。
- 游客来源地：省级 Top 排行 + 地图飞线/点状汇聚动效（Mock 数据）。

#### SR-04 应急事件地图闪烁与即时提醒
- 新事件产生时，地图对应坐标红色脉冲闪烁 + 顶部弹窗提醒音（可静音）。
- 事件来源：工作台人工接报（AD-05）；大屏以 **5 秒间隔短轮询**事件接口获取增量（按最后拉取时间/最大 ID 增量请求），状态变化最迟约 5 秒内呈现；页面不可见时自动暂停轮询。
- 事件级别颜色：蓝/黄/橙/红四级。
- 一期不引入 SSE/WebSocket（同步 Flask + gunicorn sync worker 下长连接需要额外引入 gevent 并专项配置 Nginx，收益与大屏数量不匹配）；SSE 列入二期备选，前提是后端补齐 gunicorn+gevent 并在 Nginx 关闭 `proxy_buffering`。

#### SR-05 应急事件处置状态跟踪
- 右侧事件列表展示进行中事件：标题、级别、地点、上报时间、当前状态（待处理/处置中/已闭环）。
- 点击事件查看处置时间线（每次处理动作、处理人、备注、时间），闭环事件自动归档至历史列表。

#### SR-06 热度榜与热门路线排行
- 16 取景地热度榜（Mock 综合评分：客流 + 收藏 + 评价），TOP3 特殊样式。
- 热门行程路线 Top5（基于门户行程数据聚合，数据不足时 Mock 补位）。

#### SR-07 评价与资讯滚动播报
- 底部滚动条轮播最新资讯公告标题（取自 AD-04 已发布内容）与最新游客评价摘要。

#### SR-08 实时天气与空气质量
- 展示山西省/重点城市天气、温度、风力、空气质量 AQI；数据来自真实天气 API（见 4.2），后端缓存，避免高频调用。

#### SR-09 场景自动巡航与手动交互
- 无操作 N 分钟（可配置，默认 3 分钟）后进入自动巡航：地图按预设取景地序列依次飞行定位、联动右侧数据切换。
- 支持鼠标/触摸随时打断；支持巡航路线在 AD-07 配置。

#### SR-10 视频监控点位占位
- 地图上以摄像头图标标注监控点位（点位可在工作台维护）；点击提示"视频系统二期接入"。一期不接入任何视频流，不产生流媒体服务依赖。

### 3.3 PC 运营工作台

#### AD-01 取景地内容管理
保留并深化现有 CRUD：名称、城市、经纬度（地图选点自动回填）、分类标签、封面图/图集、富文本介绍、开放时间、建议游玩时长、状态（上架/下架）、排序；列表分页、按城市/关键词筛选。

#### AD-02 用户管理与角色权限
- 内置角色：超级管理员、运营人员、值班人员；菜单与按钮级权限。
- 用户列表、启停用、重置密码；游客账号（手机号/微信）可查看可禁言，不可改其登录凭证。

#### AD-03 评价管理
评价列表、按评分/关键词筛选、违规评价下架、评价回复。

#### AD-04 资讯公告管理（新增）
- 富文本编辑器发布图文公告/资讯/活动，支持封面、分类、置顶。
- 状态：草稿 / 已发布 / 已下架；支持定时发布时间；发布后门户资讯栏目（PR-08）与大屏滚动条（SR-07）同步可见。

#### AD-05 应急事件接报与工单处置（新增）
- 人工录入事件：标题、级别、类型、关联取景地或地图点选坐标、描述。
- 工单流转：待处理 → 处置中（指派/认领、填报处置措施）→ 已闭环（填报结果）；全过程留痕，生成处置时间线。
- 提交后大屏经短轮询在约 5 秒内感知并闪烁提醒（SR-04）。

#### AD-06 数据看板
在现有统计基础上深化：用户量、收藏量、评价量、行程量、资讯阅读量、各取景地热度趋势图（时间区间可查）。

#### AD-07 大屏配置
单例配置页：16 地最大承载量阈值、客流轮询间隔、巡航闲置时长与路线、板块显隐开关、监控点位维护、大屏访问令牌生成与有效期设置。

#### AD-08 操作审计日志
记录管理端关键操作（登录、增删改、事件处置、配置变更）：操作人、模块、动作、对象、IP、时间、详情；支持检索与导出，日志留存 ≥ 6 个月。

### 3.4 游客 Web 门户

#### PR-01 首页与取景地浏览
首页按黑神话国风暗金风格重做：主题 Banner、取景地卡片、热门路线、资讯入口、天气模块；保留城市筛选与关键词搜索。

#### PR-02 地图浏览
OpenLayers 2D 地图为主：可配置底图切换（天地图默认 / OSM / 高德）、取景地点位聚合与弹窗；保留现有 Cesium 3D 切换入口，不新增 3D 功能。

#### PR-03 详情 / 收藏 / 评价
保留现有功能并做视觉升级：图集、介绍、天气小卡、收藏、1~5 星评分 + 文字评价（一人一景一条）。

#### PR-04 多日行程规划
保留多日行程创建/编辑、拖拽排序；每段路线调用真实导航服务展示驾车距离与耗时（PR-07）。

#### PR-05 空间分析
保留缓冲区分析、最短路径等现有教学/演示能力，入口在地图页；前端 Turf.js 与后端 PostGIS 双实现保持不变。

#### PR-06 实时天气
取景地详情与首页展示真实天气（后端代理天气 API，密钥不下发前端）。

#### PR-07 真实导航
行程规划与地图页调用真实路径规划服务（天地图/高德可配置），展示路线、距离、预计耗时；**高德结果为 GCJ-02 坐标，叠加天地图底图前必须经坐标转换工具纠偏**。

#### PR-08 资讯公告（新增）
资讯列表（分类、分页、置顶标识）与图文详情页（阅读量统计）；门户需做基础 SEO（标题/描述），沿用现有 SEO 方案。

### 3.5 认证与权限（统一）

#### AU-01 手机短信验证码登录
- 游客输入手机号 → 发送 6 位验证码（第三方短信服务，后端发码、限频：同号 60s 一次、每日 10 次）→ 校验通过自动注册/登录并签发 JWT。
- 开发环境提供固定万能验证码（仅 `.env` 开关开启时生效，生产强制关闭）。

#### AU-02 微信授权登录
- 微信开放平台"网站应用"OAuth 授权，获取 openid/unionid 与昵称头像；首次登录自动建号；提供"账号绑定/解绑手机号"。
- 若开放平台审核未按期完成，一期可先上线短信登录，微信登录作为开关功能后置，但用户表与登录接口需提前兼容。

#### AU-03 工作台登录与 RBAC
- 用户名密码（bcrypt 校验）+ 图形验证码（防爆破，可选开关）；JWT 有效期与刷新策略沿用现有 7 天设计并支持服务端吊销。
- 路由守卫 + 后端接口双层鉴权。

#### AU-04 大屏访问令牌
- 大屏不做交互登录：通过 AD-07 生成的一次性/长效令牌进入（URL 携带），令牌可设置有效期与 IP 白名单，可在后台随时吊销。

#### AU-05 SSO 扩展点
认证模块按提供者（Provider）模式抽象，预留 OAuth2/CAS 适配接口，一期不实现对接。

| EXT-01 | 底图瓦片 | 2D/3D 地图底图 | 天地图（默认）、OSM、高德 | 多源图层配置化；天地图 Key 以客户主体申请；高德图层 GCJ-02 |
| EXT-02 | 天气 | SR-08 / PR-06 | 和风天气（QWeather） | 服务端代理，按城市缓存 30 分钟；含 AQI |
| EXT-03 | 路径导航 | PR-07 / 行程 | 天地图驾车规划 或 高德路径规划 2.0 | 可配置切换；结果坐标按底图源做转换 |
| EXT-04 | 短信 | AU-01 | 阿里云短信 / 腾讯云短信 | 需企业签名与模板审核；限频策略在后端实现 |
| EXT-05 | 微信登录 | AU-02 | 微信开放平台（网站应用） | 需企业资质 + 审核，周期长，尽早申请 |

| VisitorOrigin（Mock） | province、count、location_id、recorded_at | 来源地分布 |

### 5.3 空间数据与能力口径

延续现有方案：GeoJSON（EPSG:4326）作为标准交换格式；PostGIS 空间查询（ST_DWithin 等）；Turf.js 前端分析；Shapefile 导入导出能力保留。

为避免三套空间库并存导致结果口径漂移，各能力的生产口径定死如下，概要设计与代码评审以此为准：

| 能力 | 唯一负责方 | 说明 |
|---|---|---|
| 游客可见的路线、距离、耗时（行程/地图） | 外部真实导航服务（EXT-03） | NetworkX 直线图结果不得在同一界面与之并存 |
| 地图交互分析（缓冲区、测量、点面判断） | 前端 Turf.js | 缓冲以米为单位时先投影再计算 |
| 服务端空间查询（半径检索、空间过滤） | PostGIS（ST_DWithin 等）+ GIST 索引 | 业务接口的空间过滤唯一入口 |
| Shapefile 导入导出、批量空间处理 | GeoPandas/Shapely | 仅用于文件处理与批处理场景，不写在线接口 |
| NetworkX 最短路径 | 保留为教学/算法演示 | 界面标注"理论直线路径"，不作为出行建议 |
| 坐标存储 | 统一 EPSG:4326 | 高德 GCJ-02 数据入库/渲染前必须转换 |

### 5.4 数据源适配层与 Mock 策略（关键架构要求）
- 后端定义统一数据接口契约，至少包含：`get_realtime_flow()`、`get_flow_history()`、`get_visitor_origins()`、`get_event_feed()`、`get_heat_ranking()`。
- 每个接口提供两个实现：`MockProvider`（一期默认）与 `StubProvider`（真实系统占位，返回 501/空集并写日志）；通过环境变量 `DATA_PROVIDER=mock` 切换。
- Mock 发生器：按各取景地承载量阈值生成符合昼夜曲线的合理波动数据，由后端集成 **APScheduler** 的定时任务按分钟写 FlowSnapshot（不引入 Celery/Redis）；提供"大客流演练""事件注入"等演示控制开关（仅管理员可调，生产环境须经鉴权并留痕）。
- 二期对接票务/信令时仅新增 Provider 实现，上层路由、序列化、前端代码零改动。

### 5.5 数据备份与生命周期
PostgreSQL 数据卷每日定时 `pg_dump` 备份并保留 ≥ 14 天；迁移脚本通过 Flask-Migrate 管理；seed 脚本可重建基础数据。

时序类数据表必须有生命周期设计，防止无限膨胀：
- `FlowSnapshot`、`VisitorOrigin` 为分钟级模拟数据，明细默认保留 30 天，由 APScheduler 每日清理过期行；需要长期趋势时按小时/天聚合到汇总表（聚合粒度与表结构在概要设计中定义，保留期可配置）。
- `AuditLog` 保留 ≥ 6 个月后按策略归档/清理。
- 清理动作纳入运维手册，首次上线前验证清理任务执行情况。

## 6 非功能需求

### 6.1 性能（NF-PERF）
- 容量目标：游客门户并发在线 < 200、工作台同时在线 < 50；大屏单端常驻。
- 常规接口 P95 响应 < 500ms（设计目标，验收前以真实压测报告为准，当前仓库无压测数据）；大屏首屏加载目标 < 5s。
- 客流数据 30~60s 轮询；应急事件 5s 短轮询增量拉取，状态变化最迟约 5s 内呈现。
- 轮询接口必须返回轻量增量数据并设置服务端缓存/限频，避免多块大屏同时轮询打满单机。
- 前端路由懒加载、manualChunks 分割；地图瓦片与静态资源开启 Nginx gzip/缓存。

### 6.2 安全（NF-SEC）
本项目不做等保测评，但默认满足以下安全基线：
1. 全站 HTTPS（Nginx + 证书，HTTP 自动跳转）。
2. 密码 bcrypt 加盐；JWT 签名密钥与所有第三方密钥环境变量化，不入库不入 Git。
3. 接口限流（登录、发码、写操作），防刷防爆破；CORS 白名单。
4. 输入校验与参数化查询（SQLAlchemy 防注入）；富文本内容服务端白名单过滤后存储，前端防 XSS。
5. 管理端操作全量审计（AD-08）；日志留存 ≥ 6 个月，日志中脱敏手机号。
6. 大屏令牌可吊销、可限 IP、有有效期。
7. 生产环境关闭 Flask Debug、固定万能验证码与 Mock 演示开关的公网入口（加管理员鉴权）。

### 6.3 可用性与可靠性
- 单机部署可用性目标 99%（非 7×24 关键系统）；Docker 异常退出自动重启策略。
- 第三方接口故障自动降级：天气/导航失败显示"暂不可用"而不白屏；轮询请求失败按退避策略自动重试，接口持续异常时不打满服务器。

### 6.4 兼容性
- 桌面：Chrome/Edge 最近两个大版本；分辨率 1366×768 至 4K。
- 门户移动浏览器自适应（手机上可浏览与查看，不作为独立移动端产品）。
- 大屏：基于 1920×1080 等比缩放适配，含超宽拼接屏。

### 6.5 可维护性与可扩展性
- 删除 TS 版后端后，后端保持应用工厂 + Blueprint 分层；新增数据源 Provider 不影响现有代码。
- 前端三端共享 API 层与类型定义；底图、Provider、第三方服务全部配置化。
- 接口遵循现有 RESTful 约定并补充 **Swagger/OpenAPI 文档**。

### 6.6 可观测性

- 结构化应用日志（按天滚动、区分级别）；关键接口请求日志；Mock 数据开关操作留痕。
- 健康检查：现有 `/api/health` 仅返回时间戳（见 server/app.py），一期需扩展为含数据库连通性探测（如 `SELECT 1`），区分存活/就绪状态，供 Nginx/运维探活。
