## 1 引言

### 1.1 编写目的

本文档定义"悟空识古"一期全部功能与非功能需求，作为设计、开发、内容生产、测试、部署与验收的共同依据。

### 1.2 项目背景与 Pivot 决策

项目原为《黑神话：悟空》山西取景地 WebGIS 演示项目（Vue 3 + Cesium/OpenLayers + Flask + PostGIS），曾规划升级为 B2G 文旅指挥平台（V1.0/V1.1）。经 2026-09-16 竞品调研与痛点再论证，确认原方向存在致命平替问题：

| 原方向面临 | 事实依据 |
|---|---|
| 指挥大屏红海 | 海康 iScenic、麦扑文旅（8000+ 景区、12+ 省文旅厅）等厂商拥有"客流硬件—数据—大屏"闭环；本项目一期只有 Mock 数据，无买单理由 |
| 打卡/路线被官方覆盖 | 山西省文旅厅官方"跟着悟空游山西"（通关文牒、91 打卡点、AR 印章）与"晋享美好"小程序已免费提供 |
| 通用 AI 导游爆发 | 黄小西、杭小忆、AI 游利川等 2025 年起密集落地，"AI 导游"本身已是平替 |
| 数据口径修正 | 游戏全国 36 处取景地中山西占 **27 处**（省级文旅厅口径），现有数据库仅 16 处，需更新 |

据此确立新定位：**游戏场景 × 现实古建的深度对照内容产品**——现有三层竞品（官方打卡=签到层、通用 AI=问答层、G 端硬件=监控层）均未覆盖"游戏内容 × 古建专业知识"的交叉深度地带。详细论证见附录 A。

### 1.3 文档范围

一期涵盖：响应式行前门户、Web 采编后台、统一后端（含 AI Provider 抽象）、内容生产规范、四大内容模块。

一期明确**不做**：微信小程序/APP、指挥调度大屏、米级机位导航、AR 取景、现场拍照识别、UGC 社区、支付交易、实地采编依赖。

| 术语 | 说明 |

## 2 产品总体描述

### 2.1 产品定位

> **《黑神话：悟空》山西取景地现场寻迹指南**：从游戏画面找到现实原型；到达景点后，按建筑区域、参观顺序和辨认特征找到对应物。AI 作为采编能力，不作为前台核心卖点。

- **人群**：古建/文博/摄影/研学深度爱好者 + 想"玩懂"游戏场景来源的游戏粉丝（非泛游客）。
- **一期核心人群**：玩过游戏、准备寻找现实原型的游客；次要人群为已经到达景点、临时查询游戏关联的游客。
- **核心痛点**：现场看不懂（导游讲传说、讲解器背简介、构件级信息缺失）；行前功课难（资料散落在论文/专著/县志/博主考据中，无权威整合）。
- **差异化壁垒**：结构化的"游戏×古建"对照知识 + 信源可信度标识。内容质量是唯一护城河。
- **商业模式**：一期不谈收入，做作品演示级标杆；二期视数据与口碑再议 B 端采购或内容付费。

### 2.2 成功标准（一期验收口径）

1. 样板取景地 1 个、对照条目 10~15 条全部走完核查工作流并发布，信源齐全、零事实硬伤。
2. 门户四模块（图鉴/字典/信息卡/路线）完整可用，移动浏览器现场查阅体验顺滑。
3. AI 三处能力位（起草、讲解、问答）以 Mock 形态完整呈现，讲解应答来自真实预置知识卡片。
4. 可作为投标/谈客户/作品集的高质量演示。

### 2.3 运行环境

- 单台云服务器（公有云），Docker Compose；PostgreSQL 16 + PostGIS 3.4 容器。
- 客户端：Chrome/Edge 最新版桌面浏览器；移动端为响应式网页（手机浏览器现场查阅），非原生体验承诺。

### 2.4 设计约束

1. **开发者约束（既定事实）**：单人 + vibe coding，只会 JS/Vue/OL/Cesium/Flask 栈。技术选型不得引入需要学习新范式的框架；架构必须简单到单人可维护。
2. 后端唯一基线：**Flask + SQLAlchemy + GeoAlchemy2**；`server/src` 下 TS/Express/Prisma 代码删除（首个任务）。
3. 前端基线：Vue 3 + TS + Vite + Pinia；门户国风视觉自研 CSS token；采编后台用 **Element Plus**；图表一期需求有限，ECharts 列为可选（若看板需要再引入）。
4. 内容生产约束：**无实地采编**。现实侧图片全部线上获取；游戏截图依赖授权渠道。
5. AI 约束：一期**全 Mock**（预置真实知识卡片应答），AI Provider 抽象保证后期切换真实国产 API（DeepSeek 类文本 + 通义 VL 类视觉）零改造。
6. 数据范围：27 处山西取景地（由现有 16 处更新扩充），不做多景区层级/多租户。
7. 性能规模：演示级（并发 <200），不引入 Redis/MQ/搜索中间件。

### 2.5 假设与依赖

- 游戏截图授权渠道真实有效，上线前完成书面确认（范围：截图数量、载体、期限）。
- 用户本人承担"AI 起草→人工核查"中的核查职责（唯一事实把关人，工作量已计入排期）。

### 3.2 行前门户（PN）

**PN-01 首页与图鉴浏览**
- 国风暗金视觉（CSS token 自研，不用 Element 默认样式）；首页含主题 Banner、精选条目、取景地入口、路线入口。
- 图鉴列表支持多维筛选：按取景地 / 朝代 / 现实文物类型（木构/彩塑/壁画/悬塑/构件）/ 游戏场景分类；关键词搜索（名称/朝代/构件术语）。

**PN-02 对照条目详情（核心页面）**
- 布局：游戏画面与现实文物照片**双图对照**（支持滑动/并排切换）；条目正文含"游戏化用说明、文物档案（朝代/年代/规格）、价值与看点（构件级）、参观提示"。
- 信源区块：列出全部信源（标题+类型+链接），显示信源等级标识；未核查条目不出现（见 5.4 红线）。
- 互动：收藏（登录态）、相关词条跳转（点击正文中的构件术语弹出知识字典悬浮卡）、同取景地其他条目推荐。

**PN-03 古建知识字典**
- 术语卡（斗拱/藻井/悬塑/鸱吻/减柱造…）：定义、图示、代表实例（链回条目）、相关术语。
- 朝代年表：唐/五代/辽/宋/金/元/明各期山西木构与彩塑特征速查。

**PN-04 取景地实用信息卡片**
- 取景地详情页：简介、开放时间、门票、**预约要求、禁拍规定（可拍/禁拍/禁闪光/禁三脚架）**、交通方式、参观提示。
- 数据由采编后台维护，展示"信息更新于 X 日期"时效标识；暂不接实时数据源。

**PN-05 主题路线**
- 编辑产出的结构化路线（如"唐宋木构线""彩塑朝圣线"）：按天分组的取景地/条目序列、路线说明、简易地图示意（OpenLayers 打点，底图可配置：OSM 默认，天地图 Key 后置）。
- 不做实时导航/耗时计算（真实导航服务列为二期）。

**PN-06 用户登录与收藏**
- 保留现有 JWT 账号体系（用户名密码注册/登录）；收藏对象从"取景地"扩展为"对照条目 + 取景地"。
- 手机验证码/微信登录列为二期（既定决策：一期无短信/微信资质依赖）。

**PN-07 AI 讲解入口（Mock）**
- 条目详情页"问一问"入口：针对本条目预置问题集（如"这尊塑像为什么牛？"），Mock Provider 从知识卡片与条目内容生成结构化应答；界面显著标注"AI 助手（演示版）"。
- 一期不接真实大模型 API（SV-02 保证后期切换）。

**PN-08 移动端响应式**
- 断点适配手机浏览器；核心场景"现场查条目/信息卡"两步内可达（取景地→条目）。

**PN-10 小西天现场模式**
- 首页提供两个并列入口："从游戏找原型"进入图鉴，"我已到景点"进入现场模式。
- 一期只深做小西天，按实际参观顺序组织 10~15 个条目；用户按建筑/区域缩略图和简短路线指引寻找对应物。
- 条目首屏优先展示游戏图、现实图、三个辨认特征、所在区域、推荐观察方位与拍摄状态；不承诺精确机位、焦段、室内定位或实时导航。
- 对应关系分为"已确认 / 高度相似 / 参考元素"三级，每级公开判断依据；筛选支持只看"已确认"。
- 进入取景地后预载该地文字、缩略图与方向指引；高清图按需加载。地图失效不得阻断现场内容。
- 提供"没找到"结构化纠错，原因包括方向不清楚、区域关闭、对应物有误、拍摄规定变化；反馈仅进入后台待核查，不公开展示。

### 3.3 采编后台（ED）

**ED-01 登录与角色**
- 账号密码登录；角色：管理员（全权）、编辑（内容 CRUD）。复用现有 User 表与 JWT。

**ED-02 对照条目 CRUD 与核查工作流**
- 状态机：`草稿 → 待核查 → 已核查 → 已发布`（支持退回草稿）。
- 编辑表单：游戏场景信息（名称/分类/游戏图）、现实文物信息（名称/类型/朝代/年代细节）、正文富文本（wangEditor）、看点结构化字段、关联取景地、关联字典术语、信源编辑器（增删改，逐条填类型/标题/URL/引文）。
- 状态流转记录操作人与时间；仅"已核查"状态可发布（工作流强制，前端禁用+后端校验双层）。

**ED-03 AI 起草工作台（Mock 实现）**
- 选择游戏场景与文物类型 → Mock Provider 按条目模板生成结构化初稿（各字段 + 信源占位提示）→ 编辑修改后保存为草稿。
- 真实 AI 起草（调 LLM 生成+自动引文标注）列为二期，接口契约预留（SV-02）。

**ED-04 素材库与版权合规看板**
- 上传/登记素材：类型（游戏截图/现实照片/示意图）、License（official/cc0/cc-by/placeholder）、署名与来源 URL。
- 合规看板：统计各条目素材 License 构成，**placeholder 占位素材高亮告警**；"待替换清零"是上线前置检查项。

**ED-05 字典/信息卡/路线管理**：三类内容的 CRUD，模式同条目（轻量工作流：草稿→发布）。

**ED-06 取景地管理**
- 现有 16 处数据**更新并扩充至 27 处**（名称/城市/经纬度/简介/分类），保留 geom 空间字段；支持地图选点校验坐标。

**ED-07 操作审计**：登录、发布、删除、素材 License 变更留痕。

### 3.4 服务端（SV）

**SV-01 REST API + Swagger**：flask-smorest 生成 OpenAPI 文档；沿用现有 Blueprint 分层。
**SV-02 AI Provider 抽象层**：
- 契约：`draft_entry(scene, target_type)`、`explain(entry)`、`chat(entry, question)`、`plan_route(prefs)`（预留）。
- 实现：`MockAIProvider`（一期默认，基于知识卡片/条目内容的模板化应答）与 `ApiAIProvider`（二期，DeepSeek/通义 VL 等）。
- 切换：环境变量 `AI_PROVIDER=mock|api`，上层代码零改动。

**SV-03 检索**：PostgreSQL tsvector 全文索引（条目标题/正文/术语）+ 标签/朝代/类型组合筛选；不引入 ES。
**SV-04 认证鉴权**：JWT + bcrypt；管理端接口 RBAC；登录限流（Flask-Limiter）。
**SV-05 健康检查**：`/api/health` 扩展数据库连通探测（`SELECT 1`）。
**SV-06 空间分析 API 保留**：现有缓冲区/最短路径等接口保留（支撑路线地图示意与既有能力），门户入口弱化。

## 4 内容生产规范（本产品头号风险控制）

### 4.1 对照条目结构模板

```
条目标题：〔游戏场景名〕×〔现实文物名〕
├─ 游戏侧：场景名/BOSS 名、出现章节、画面截图（License: official）
├─ 现实侧：文物名称、类型、朝代、年代细节、文保级别、所在取景地
├─ 对照说明：游戏如何化用现实（构图/造型/彩塑群像对应关系）
├─ 价值与看点：构件级（例：悬塑层次、梁架结构、壁画画法）
├─ 参观提示：最佳观赏位置/光线、禁拍规定
├─ 信源列表：≥2 条（其中官方文保/学术类 ≥1），标注类型与引文
└─ 可信度：由信源等级自动计算展示
```

### 4.2 信源分级与可信度

| 等级 | 类型 | 示例 |
|---|---|---|
| S | 官方文保资料 | 国保单位档案、文保所官方介绍、博物馆官方 |
| A | 学术/出版物 | 论文、《山西古建筑文化综论》等专著、设定集官方说明 |
| B | 权威媒体/机构 | 省文旅厅发布、新华网等报道 |
| C | 社区考据 | 玩家 wiki、资深博主考据（仅可作旁证，不可单独支撑事实性表述） |

规则：每条目 ≥2 个信源且含 ≥1 个 S/A 级；C 级单独支撑的观点必须用"一说/据考"措辞。

### 4.3 生产流水线（先样板后批量）

1. 选定样板取景地（建议隰县小西天：悬塑对标材料丰富）。
2. AI（Mock 模板）起草 10~15 个条目初稿 → 用户逐条核查（对照信源）→ 修正 → 标记已核查 → 发布。
3. 复盘流水线耗时与模板缺陷，形成《内容生产手册》后再批量复制（批量属二期/一期后半可选）。

### 4.4 红线（强制）

1. **事实红线**：无信源不入库、未核查不发布；朝代/年代/构件名称错误视为 P0 缺陷。
2. **版权红线**：游戏截图必须有书面授权（微信式审核同样适用于对外演示场景的发布平台条款）；现实照片上线前必须为 CC 协议图或官方授权图；**placeholder 素材只允许存在于内部开发环境，对外演示/上线前清零**。

## 7 非功能需求

- **性能**：常规接口 P95 < 500ms（设计目标，验收前以本地压测为准）；门户首屏 < 3s（内容型站点，图片懒加载 + WebP + Nginx gzip）。
- **安全基线**（沿用 V1.1 结论）：HTTPS、bcrypt、JWT、登录限流、CORS 白名单、**富文本服务端 bleach 白名单消毒**（条目正文是 XSS 主要入口）、SQL 参数化、审计日志 ≥6 个月、密钥环境变量化。
- **兼容性**：Chrome/Edge 最新两版桌面；iOS/Android 主流浏览器响应式（非原生体验承诺）。
- **可观测性**：结构化日志按天滚动；`/api/health` 含 DB 探测。
- **可维护性（vibe coding 专项）**：模块边界以本文档与后续概要设计为准；Entry/素材/工作流等核心模型必须先写迁移再写代码；避免为单一页面引入新框架。
